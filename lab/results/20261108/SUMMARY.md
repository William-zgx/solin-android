## What this means for the phone

### Suite F: production `.litertlm` files on LiteRT-LM 0.12.0

Host label: **devbox CPU / LiteRT-LM 0.12.0 (production .litertlm)**. Same weights, quantization, chat
template and runtime version as the phone; only the hardware differs. Driven through
`lab/scripts/litert_shim.py`. Latency is x86 devbox CPU, not phone latency. E2B and E4B ran
concurrently, each on about 2 cores of a 32-core host, so do not compare their wall times directly.

**(a) Does production's text `call:` prompt work with the shipped 270M file? No — every call
overflows the file's 1024-token context.** This is not a quality result and must not be read as a score.

| model | suite / mode | cases | outcome |
| --- | --- | --- | --- |
| `litert/mobile-actions-270m` | B `M-full` | 151 | 151/151 errored (engine rejected the call: context overflow) |
| `litert/mobile-actions-270m` | B `M-full-fix` | 151 | 151/151 errored (same) |
| `litert/mobile-actions-270m` | C `N-full` | 151 | 151/151 errored (same) |
| `litert/mobile-actions-270m` | C `N-topk` | 151 | 112/151 errored; 39 answered |
| `litert/mobile-actions-270m` | B `M-topk` | 151 | 151 answered, 0/100 tool requests right |
| `litert/mobile-actions-270m` | B `M-topk-fix` | 151 | 151 answered, 0/100 tool requests right |

Evidence (engine stderr, quoted in the run log): `INVALID_ARGUMENT: Input token ids are too long.
Exceeding the maximum number of tokens allowed: N >= 1024`. Measured N: text `M-full`/`M-full-fix`
2632–2672; native `N-full` 7916–7946; `N-topk` 1026–1283, where 112 of 151 cases exceed 1024. The shim
never truncates: an overflow is recorded as an error, and the JSONL keeps the error string.

**Production consequence.** The default path builds the model call without a tool shortlist:
`InitialToolPlanner.kt:125` calls `actionPlanningRuntime.plan(input, actionModelPath)`, and the
two-argument `plan` (`action/ActionPlanningRuntime.kt:79` → `:140`) prompts with the whole registry
(`actionPrompt(input, toolSpecs?.takeIf { it.isNotEmpty() } ?: toolRegistry.specs())`,
`action/ActionPlanningRuntime.kt:146`). With the shipped `mobile-actions_q8_ekv1024.litertlm` every such
call overflows, the model contributes nothing, and the rules decide. The token count depends on the
model file and tokenizer, not the host, so this transfers to the phone; the exact on-device error is
**pending device confirmation**.

**(b) Native tools vs the text prompt.** Native tools are the only path that runs at all on the 270M,
because the text prompt overflows. On E2B and E4B the native path parses cleanly on the production
file: 136/151 (E2B) and 133/151 (E4B) `N-topk` answers arrive as `call`, and the rest are 12–18 plain
`text` answers plus 3 engine errors (E2B). The model's own `tool_call:name{...}` rendering is converted
to a native `tool_calls` array by the shim, exactly as the app reads a native call, so nothing here
depends on the app's `call:` text parser. Top-8 native accuracy: E2B 75/100 tool requests right,
E4B 77/100. Full native rows are in the Suite B/C tables above; treat the cross-host comparison as a
direction only, since the Ollama native runs used a different runner.

With a retrieved top-8 the text prompt runs, and this is the decisive experiment of Suite F:

- **E2B `M-topk` on the production `.litertlm`: 0/100, all 151 invalid with `Unknown tool: function`.**
  E2B emits a well-shaped call whose tool name is the prompt's literal placeholder:
  `call:function {"arg":"open_app_by_name":{"appName":"微信"}}` for 别启动微信,
  `call:function {"arg":"share_text":{"text":"明天十点开会"}}` for 不要把这段文字分享出去. The arguments
  are nested inside `"arg"` too, so this is not one missing token: the model copies the prompt's example
  shape. **E4B `M-topk` fails identically — 151/151 `Unknown tool: function`** — so this is not a
  small-model limitation; a stronger model copies the placeholder just as faithfully.
- **E2B `M-topk-fix` — the same run with the placeholder rewritten: 77/100 tool requests right,
  149/151 parse as `call`.** This is the ablation that settles the cause. The only prompt change is
  `call:function {"arg":"value"}` → `call:函数名 {"参数名":"值"}（函数名换成下面列表里的一个函数）`, in
  both the user prompt and the system instruction
  (`lab/.../OllamaActionPlanningRuntime.kt`, `PlaceholderAblation`). The text path went from 0/100 to
  77/100, and from zero valid parses to essentially all of them. The prompt, not the model, is what
  breaks the text path. It is also far more eager: 49/51 false positives on no-tool requests (it calls
  a tool for 别启动微信), so overall it is 72/151 against `R` at 127/151 — a raw-prompt model swap is not
  an improvement even once it parses.
- **270M `M-topk` / `M-topk-fix`: 0/100 tool requests right.** All 151 answered and none parsed; the
  answers are plain prose that *mentions* the placeholder ("my capabilities are limited to calling
  functions like \"function {\"arg\":\"value\"}\""). It does not attempt a call at all, in either mode, so
  the placeholder ablation tells us nothing on this model.

So production's `actionPrompt` placeholder breaks the text path on both files that can actually run it,
and replacing it recovers 77/100 tool selection. `M-full-fix` / `M-topk-fix` are the lab-only ablation,
not what the app sends. **Fixing the production prompt text is the cheapest available win and should
come before anything else is tried; native tool declarations remain the better long-run shape, because
they avoid the text format entirely.** Either way the gain is tool *selection*, not intent — the
false-positive rate says the model still needs a gate in front of it (see the composite table).

**(c) False positives on the 51 no-tool cases — the reason no ungated mode beats `R`.** Every model mode
executes a tool on requests that want none:

| mode | false positives on 51 no-tool cases | overall (151) |
| --- | --- | --- |
| `R` (rules) | 0/51 | 127/151 |
| E2B `N-topk` | 39/51 | 83/151 |
| E2B `M-topk-fix` | 49/51 | 72/151 |
| E4B `N-topk` | 35/51 | 93/151 |
| 270M `N-topk` | 6/51 | 61/151 (112 errored) |

The text modes that fail to parse are not false positives in this sense — an unparseable call executes
nothing — which is exactly why E2B `M-topk` shows 0/51 while being useless at the same time. The mode
that parses best is also the mode that acts most wrongly: picking a tool is easier than deciding not to.

This is the measured reason the composite table is the interesting one. Filling only the 74 cases the
rules left alone, every model mode scores **below `R`'s 127/151** (`M-topk-fix` 85, `N-topk` 96 and 100
for E2B/E4B); with the action gate in front, the same runs score **above** it — E2B 129/151 (+7/−5) and
E4B 133/151 (+8/−2). The gate, not the model, is what makes the model usable.

**(d) 270M `M-full` prompt overflows.** 151 of 151. The prompt is 2632–2672 tokens against a
1024-token limit, so there is no case where the production prompt fits.

E2B LiteRT also wraps 62/151 gate answers in a markdown code fence (Ollama: 0, E4B: 0). The lab's own
reader strips fences (`ActionGateSuiteTest.kt:88`, `RoutingSuiteTest.kt:151`), so all 151 parse — but
that stripping is **lab code, not production code**. Production's `parseDecisionResponse`
(`runtime/CodivDecisionModelRouter.kt:88`) calls `JSONObject(raw)` on the whole string and has no fence
handling, so a fenced answer would fail as `not_json` and the rule placement would stand (fail-closed,
but 41% of the gate's answers lost). Before this shape ships, confirm whether the production LiteRT
path can emit a fenced answer; the nearest production stripper,
`ActionPlanner.stripSingleMarkdownFence` (`action/ActionPlanner.kt:402`), is on the `call:` text path
only and would not help here.

**Suite D on the production file: the best LiteRT accuracy, but only the answer, not the transport.**
25/26 routing decisions right against 15/26 for the rules, with every verdict above the 0.9 gate
(`effectiveCorrect` 25/26 — the one miss stays wrong through the gate): local gold 15/15, remote gold
10/11. The single miss, `reasoning_logic` (a three-person liar puzzle), went `local` at 0.95, which is
the one direction where a wrong verdict silently degrades the answer instead of failing visibly. The
task is a single small-choice prompt, which is why it fits the 1024-token context and the 2B model
handles it; it is the shape most worth shipping early.

Read the accuracy, not the wiring. The lab asks the question in a flat `{"choice", "confidence"}` shape
under a system prompt, while production's only router, `CodivDecisionModelRouter`, posts to a remote
`/systemone` endpoint and parses a nested `{"answers": {"placement": {...,"probabilities":{...}}}}`
(`runtime/CodivDecisionModelRouter.kt:88`). The question text is shared; the response shape and the
local execution path are not, and the app has no local-model decision parser at all. So this measures
whether the file can answer the routing question, not whether the app can consume the answer.

**`token recognition error` lines.** 20 lines in the shim log (`line 1:10 token recognition error at:
'勿'`, and `'"'` variants). Cause: LiteRT's FunctionGemma call parser parses the *generated text* as a
native call. When the text prompt literally contains `call:function {"arg":"value"}`, the parser hits
the quote characters; on CJK output it hits the first CJK character. Reproduced deterministically on
the 270M file: the same conversation is clean with native `tools` and warns as soon as the prompt
contains the placeholder line. It is a parser warning on unusable output, not a second failure mode;
the native path emits proper `tool_calls` and does not warn.

### Ollama run (devbox CPU / Ollama 0.40.13)

1. **The production rules stay the floor.** `R` scores 127/151 (76/100 tool requests, 51/51 no-tool).
   Nothing measured here beats it as a standalone first-tool planner on this host.
2. **The action gate is the strongest single result.** Suite E (JSON `{action, confidence}`, >= 0.9)
   scores 134/151 for E2B and 132/151 for E4B, with 97% and 95% precision on the cases where it opens.
   On the 74 rule-gap cases it is 70/74 (E2B) and 69/74 (E4B). E2B is the better gate on CPU: it opens
   on one fewer no-tool case. This is the shape worth prototyping: rules decide the tool, a small model
   decides only *whether to act*.
3. **`R` + gate + `N-full` is the best composite in the table, and E4B leads it (143/151).**
   E4B: the gate opens on all 74 gap cases, `N-full` supplies 28 answers, +21/−5 against `R` alone.
   E2B: 138/151, 25 answers, +13/−2. `N-full` alone is weaker for E4B than for E2B on no-tool requests
   (45/51 false positives vs 34/51), yet the gate absorbs that: it keeps the gate's 95% precision and
   gains more tool cases. Both composites depend on the model answering *without executing anything
   itself* — the gate is the safety valve.
4. **FunctionGemma 270M in Ollama is the BASE model, not the production fine-tune.** Do not read its
   numbers as the shipped model. On this base build it refuses or chats on all 151 cases in the `call:`
   text format and with native tools over the full registry (0/100 tool requests, 51/151 overall, all of
   them "correct" only because refusing a no-tool request is correct). With a top-8 shortlist it emits
   some calls (19/100 tool-correct, 2/51 false positives), mostly in Gemma's own `tool_call:` form rather
   than the app's `call:`. The production fine-tune is measured in Suite F below (LiteRT-LM on
   `mobile-actions_q8_ekv1024.litertlm`); nothing in this Ollama section measures it.
5. **Native tools do not fix intent.** E4B `N-full` is 95/100 tool requests with pinned arguments but
   45/51 false positives on no-tool requests; E2B is 89/100 and 34/51. Choosing a tool is easier than
   deciding not to.

### In-app search: `在淘宝搜索牛奶` (production gap, on `edge-lab/integration`)

Confirmed a real rule gap, and a real skill gap, not a missing measurement.

- The production rules return no tool. `MobileActionPlanner.inferDraft`
  (`action/ActionPlanner.kt:99`) has no `在X搜索Y` branch, and the one rule that could match,
  `AppNavigationActionParser`, requires a leading 打开/启动/进入
  (`action/AppNavigationActionParsers.kt:160`), then rejects anything containing 搜索
  (`action/AppNavigationActionParsers.kt:342`, `looksLikeAppNavigationNonAction`).
- The open-then-search skill exists but needs a leading launch verb:
  `EXTRACT_OPEN_APP_UI_SEARCH_REQUEST_ZH1_REGEX` (`skill/BuiltInSkillIntentMatchers.kt:201`) starts
  with 打开/启动/进入, so 在淘宝搜索牛奶 does not match it. It is reached from
  `BuiltInSkills.plan` (`skill/BuiltInSkills.kt:88`).
- `InitialToolPlanner.planToolIfSupported` (`orchestration/InitialToolPlanner.kt:211`) therefore returns
  null, and `AgentLoopRuntime` turns the run into a plain chat answer
  (`orchestration/AgentLoopRuntime.kt:562-604`). The 14 in-app-search cases in the dataset fail exactly
  here (one passes because it routes to maps).
- Only the local-model shortlist retriever knows the shape: `inAppSearchShape`
  (`tool/ToolRetriever.kt:142`) treats `在/去/到/用/打开 + 名称 + 搜索` as an `open_app_by_name` trigger.
  That helps `LocalModelFirst` only, which is debug-only and default off.

So the fix is a skill/rule for the `在X搜索Y` shape, not a prompt change. Until then, a local or remote
model is the only thing that can pick `open_app_by_name` for it.
