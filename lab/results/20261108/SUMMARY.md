### Suite F: production `.litertlm` files on LiteRT-LM 0.12.0

Host label: **devbox CPU / LiteRT-LM 0.12.0 (production .litertlm)**. Same weights, quantization, chat
template and runtime version as the phone; only the hardware differs. Driven through
`lab/scripts/litert_shim.py`. Latency is x86 devbox CPU, not phone latency. E2B and E4B ran
concurrently, each on about 2 cores of a 32-core host, so do not compare their wall times directly.

**(a) Does production's text `call:` prompt work with the shipped 270M file? No — every call
overflows the file's 1024-token context.** This is not a quality result and must not be read as a score.

| model | suite / mode | cases | outcome |
| --- | --- | --- | --- |
| `litert/mobile-actions-270m` | B `M-full` | 151 | 151/151 errored (engine rejected the call: context overflow) |
| `litert/mobile-actions-270m` | B `M-full-fix` | 151 | 151/151 errored (same) |
| `litert/mobile-actions-270m` | C `N-full` | 151 | 151/151 errored (same) |

| `litert/mobile-actions-270m` | B `M-topk-fix` | 151 | 151 answered, 0/100 tool requests right |

Evidence (engine stderr, quoted in the run log): `INVALID_ARGUMENT: Input token ids are too long.
Exceeding the maximum number of tokens allowed: N >= 1024`. Measured N: text `M-full`/`M-full-fix`
2632–2672; native `N-full` 7916–7946; `N-topk` 1026–1283, where 112 of 151 cases exceed 1024. The shim
never truncates: an overflow is recorded as an error, and the JSONL keeps the error string.

**Production consequence.** The default path builds the model call without a tool shortlist:
`InitialToolPlanner.kt:125` calls `actionPlanningRuntime.plan(input, actionModelPath)`, and the
two-argument `plan` (`action/ActionPlanningRuntime.kt:79` → `:140`) prompts with the whole registry
(`actionPrompt(input, toolSpecs?.takeIf { it.isNotEmpty() } ?: toolRegistry.specs())`,
`action/ActionPlanningRuntime.kt:146`). With the shipped `mobile-actions_q8_ekv1024.litertlm` every such
call overflows, the model contributes nothing, and the rules decide. The token count depends on the
model file and tokenizer, not the host, so this transfers to the phone; the exact on-device error is
**pending device confirmation**.

With a retrieved top-k the text prompt runs. It is worse than unusable, and this is the single
strongest finding of Suite F:

- **270M `M-topk` / `M-topk-fix`: 0/100 tool requests right**, but for a weaker reason than E2B. All
  151 answered and none parsed; 145/148 are plain prose that *mentions* the placeholder
  ("my capabilities are limited to calling functions like \"function {\"arg\":\"value\"}\""), not a
  `call:` line. The model does not attempt a call here at all.
- **E2B `M-topk` on the production `.litertlm`: 0/100, all 151 invalid with `Unknown tool: function`.**
  This one is worse and is the real evidence: E2B does emit a well-shaped call, and the tool name is the
  prompt's literal placeholder. `call:function {"arg":"open_app_by_name":{"appName":"微信"}}` for
  别启动微信, `call:function {"arg":"share_text":{"text":"明天十点开会"}}` for 不要把这段文字分享出去.
  The arguments are even nested inside `"arg"`, so this is not one missing token: the 2B model copies
  the prompt's example shape. A stronger model does not rescue the text format; only the prompt does.

So production's `actionPrompt` placeholder breaks the text path on the file that can actually run it.
`M-full-fix` / `M-topk-fix` are the lab-only ablation that replaces the placeholder; on the 270M they
do not help (the model answers in prose either way), and the `-fix` text is not what the app sends.
**This is the case for native tool declarations, or for fixing the production prompt text before
anything else is tried.**

**(b) Native tools vs the text prompt.** On the 270M, native tools are the only path that produces a
call at all, because the text prompt overflows. With `N-topk`, 39 cases answered and 18/100 tool
requests were right with 16 exact; 6/51 no-tool cases still opened a call. Native declarations are
therefore a real production option for this model; the text format is not usable at this context size.
E2B and E4B native rows are in the Suite B/C tables above; the comparison there is confounded by
different hosts, so only the 270M row is a same-file comparison.

**(c) False positives on the 51 no-tool cases.** 270M `N-topk` 6/51. The text modes never execute
anything (an unparseable call executes nothing), so they are not false positives; they are wrong tool
answers. E2B (LiteRT) and E4B (LiteRT) rows are the `errored` and tool columns in the Suite C table.

**(d) 270M `M-full` prompt overflows.** 151 of 151. The prompt is 2632–2672 tokens against a
1024-token limit, so there is no case where the production prompt fits.

**`token recognition error` lines.** 20 lines in the shim log (`line 1:10 token recognition error at:
'勿'`, and `'"'` variants). Cause: LiteRT's FunctionGemma call parser parses the *generated text* as a
native call. When the text prompt literally contains `call:function {"arg":"value"}`, the parser hits
the quote characters; on CJK output it hits the first CJK character. Reproduced deterministically on
the 270M file: the same conversation is clean with native `tools` and warns as soon as the prompt
contains the placeholder line. It is a parser warning on unusable output, not a second failure mode;
the native path emits proper `tool_calls` and does not warn.

### Ollama run (devbox CPU / Ollama 0.40.13)

1. **The production rules stay the floor.** `R` scores 127/151 (76/100 tool requests, 51/51 no-tool).
   Nothing measured here beats it as a standalone first-tool planner on this host.
2. **The action gate is the strongest single result.** Suite E (JSON `{action, confidence}`, >= 0.9)
   scores 134/151 for E2B and 132/151 for E4B, with 97% and 95% precision on the cases where it opens.
   On the 74 rule-gap cases it is 70/74 (E2B) and 69/74 (E4B). E2B is the better gate on CPU: it opens
   on one fewer no-tool case. This is the shape worth prototyping: rules decide the tool, a small model
   decides only *whether to act*.
3. **`R` + gate + `N-full` is the best composite in the table, and E4B leads it (143/151).**
   E4B: the gate opens on all 74 gap cases, `N-full` supplies 28 answers, +21/−5 against `R` alone.
   E2B: 138/151, 25 answers, +13/−2. `N-full` alone is weaker for E4B than for E2B on no-tool requests
   (45/51 false positives vs 34/51), yet the gate absorbs that: it keeps the gate's 95% precision and
   gains more tool cases. Both composites depend on the model answering *without executing anything
   itself* — the gate is the safety valve.
4. **FunctionGemma 270M in Ollama is the BASE model, not the production fine-tune.** Do not read its
   numbers as the shipped model. On this base build it refuses or chats on all 151 cases in the `call:`
   text format and with native tools over the full registry (0/100 tool requests, 51/151 overall, all of
   them "correct" only because refusing a no-tool request is correct). With a top-8 shortlist it emits
   some calls (19/100 tool-correct, 2/51 false positives), mostly in Gemma's own `tool_call:` form rather
   than the app's `call:`. The production fine-tune is measured in the D4 follow-up commit (Suite F,
   LiteRT-LM on `mobile-actions_q8_ekv1024.litertlm`); nothing in this Ollama section measures it.
5. **Native tools do not fix intent.** E4B `N-full` is 95/100 tool requests with pinned arguments but
   45/51 false positives on no-tool requests; E2B is 89/100 and 34/51. Choosing a tool is easier than
   deciding not to.

### In-app search: `在淘宝搜索牛奶` (production gap, on `edge-lab/integration`)

Confirmed a real rule gap, and a real skill gap, not a missing measurement.

- The production rules return no tool. `MobileActionPlanner.inferDraft`
  (`action/ActionPlanner.kt:99`) has no `在X搜索Y` branch, and the one rule that could match,
  `AppNavigationActionParser`, requires a leading 打开/启动/进入
  (`action/AppNavigationActionParsers.kt:160`), then rejects anything containing 搜索
  (`action/AppNavigationActionParsers.kt:342`, `looksLikeAppNavigationNonAction`).
- The open-then-search skill exists but needs a leading launch verb:
  `EXTRACT_OPEN_APP_UI_SEARCH_REQUEST_ZH1_REGEX` (`skill/BuiltInSkillIntentMatchers.kt:201`) starts
  with 打开/启动/进入, so 在淘宝搜索牛奶 does not match it. It is reached from
  `BuiltInSkills.plan` (`skill/BuiltInSkills.kt:88`).
- `InitialToolPlanner.planToolIfSupported` (`orchestration/InitialToolPlanner.kt:211`) therefore returns
  null, and `AgentLoopRuntime` turns the run into a plain chat answer
  (`orchestration/AgentLoopRuntime.kt:562-604`). The 14 in-app-search cases in the dataset fail exactly
  here (one passes because it routes to maps).
- Only the local-model shortlist retriever knows the shape: `inAppSearchShape`
  (`tool/ToolRetriever.kt:142`) treats `在/去/到/用/打开 + 名称 + 搜索` as an `open_app_by_name` trigger.
  That helps `LocalModelFirst` only, which is debug-only and default off.

So the fix is a skill/rule for the `在X搜索Y` shape, not a prompt change. Until then, a local or remote
model is the only thing that can pick `open_app_by_name` for it.
