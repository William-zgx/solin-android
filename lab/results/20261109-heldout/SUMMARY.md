## What this means for the phone

### Scope and host

This is the **different, harder, non-tuned, evaluation-only 60-case held-out set**. Do not compare its
absolute numbers with the 151-case campaign, whose cases informed prompt, rule and threshold tuning. The
only performance delta claimed here is **production gated versus rules within this same held-out set**.
No label, prompt, rule, retriever or threshold was changed after seeing these outputs.

Each run has 60 unique cases. `R-gated-e2e` used the merged production `RuleFirstGatedModel`, including
production's one whole-reply fence handling, not the lab-only fence adapter. E2B returned 26 fenced gate
replies and E4B returned none; all 33 gate calls per model parsed as valid production gate JSON, with zero
invalid gate replies. The host is **devbox CPU / LiteRT-LM 0.12.0 on the production `.litertlm` files**.
These are not device quality, latency, memory or safety-acceptance results, and no tool was executed.

### Gated versus rules, within this set

- Rules `R`: **37/60** correct, 14/29 tool-correct, 11/29 exact-args.
- E2B `R-gated-e2e`: **47/60** correct, 24/29 tool-correct, 21/29 exact-args, gate open 12; **+10**
  overall, with 10 cases fixed and 0 broken against `R`.
- E4B `R-gated-e2e`: **47/60** correct, 24/29 tool-correct, 21/29 exact-args, gate open 13; **+10**
  overall, with 10 cases fixed and 0 broken against `R`.
- Errors, including every per-call `metrics.error`: **0/60 for `R`, E2B and E4B**. Thus no partial-run
  Decision-L1 error annotation is needed; the generated tables still carry the explicit zero counts.

E2B and E4B have the same aggregate but not identical cases. E2B fixes `heldout_tool_019` (in-app search)
while E4B leaves it unanswered; E4B fixes `heldout_tool_011` (calendar) while E2B closes the gate. They
also differ in argument wording on two cases that both score correct.

### Category findings

- **Negations:** ordinary no-tool negation is **3/3 correct** and adversarial negation **4/4** for `R`,
  E2B and E4B. Manual how-to requests are **2/2** for all three, and adversarial no-tool FP is **0/7**.
- **Questions about a tool domain:** only **2/5 correct** for all three. The other three are false
  positives. Hypothetical-action requests are **1/3** for all three, accounting for the remaining two
  ordinary no-tool false positives.
- Both gated models improve reminder 1/2 → 2/2, SMS drafts 0/1 → 1/1, maps search 0/2 → 2/2,
  media 0/1 → 1/1, share 0/1 → 1/1 and polite indirect requests 0/2 → 1/2 against `R`.
- Calendar improves 0/2 → 1/2 on E2B and → 2/2 on E4B. In-app search improves 0/2 → 2/2 on E2B and
  → 1/2 on E4B. These are the case swaps behind the equal 47/60 totals.
- Unresolved on both models: timer 1/2, email draft 0/1, notes 0/1, web search 1/2, typo 0/1 and long
  request 0/1. The generated per-category table is the complete 28-category result, not a selection.

### False-positive class split

The ordinary no-tool false-positive rate is unchanged at **5/24** for `R`, E2B and E4B, on the same five
cases and with the same tools: **0 orchestration-only, 5 device/network/external-app, 4 privacy-flagged,
1 private read and 3 network-egress**. The remaining executable FP is `share_text`. These are rule-produced
plans that run before the model gate, so the gated path neither adds nor removes them.

The measured within-set gain is therefore tool coverage, not a no-tool safety improvement. Any phone
rollout decision still needs device evidence; `RuleFirstGatedModel` remains debug-only.
