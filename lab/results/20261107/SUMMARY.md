## What this means for the phone

Scope: desktop Ollama 0.40.3 on an Apple M3 Pro (MLX runner), synthetic and not held out. Nothing here is
device evidence. No phone, LiteRT-LM or GPU run is included.

1. **The rules are the floor to beat.** Production rules get 127/151 on suites B and C (76/100 tool
   requests, 51/51 no-tool requests). No model in the `call:` text format beats that alone. Rules plus a
   model fallback equal the rules for every model (127/151), because the rule gate rarely reaches the model.
2. **The bottleneck is whether to act, not which tool.** Native tool calling chooses well on tool requests
   (gemma4:e4b N-full 95/100 on tool requests with every pinned argument) but acts on no-tool requests: 34/51
   false positives for E4B (17/51 correct, table above). The placeholder ablation (`-fix`) matters for the
   `call:` format: E4B goes from 49/100 to 81/100 on the same metric once the prompt's example placeholder is
   not copied. An interim note gave 50 to 84 on a looser metric; the two are not reconciled here. That is a
   lab finding; the production prompt is not changed by this run.
3. **Any gate has to be measured as a gate.** A model that answers only the rule-gap requests is the only shape
   that could help, and the composite numbers that would show it are not computed by this run (see pending).
4. **In-app search is a real rule gap.** `在淘宝搜索牛奶` gets no tool from the rules. The open-then-search
   skill matches only a leading 打开, 启动 or 进入 (`skill/BuiltInSkillIntentMatchers.kt:202`), so the
   `在X搜索Y` shape is not handled by it. A model-driven app search exists behind `AppSearchPlanningMode`
   (`SolinAppContainer.kt:404`), but this run did not exercise it.
5. **Suite D routing.** The json-prompt routing mode scores 25/26 for E2B and 25/26 for E4B on 26 cases, against
   15/26 for rules. That is 26 cases; treat it as a direction, not a rate.
6. **Latency and device fit are unmeasured here.** The Mac timings are not comparable with a phone.
